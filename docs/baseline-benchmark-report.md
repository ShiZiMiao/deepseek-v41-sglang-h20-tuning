# DeepSeek-V4.1-Flash-1017 · 性能基线与优化报告

> 日期：2026-11-10
> 用途：§1–§5 是**优化前基线**，§6 是优化方案，§7 是**优化后实测结果**。
> 后续任何改动都以本报告的结果表为对照，用同一套压测套件复跑后逐场景比对。
> 结论先行：**预填充吞吐是唯一的主要短板，且它与并发无关、只随上下文长度下降**；
> 解码速度已由投机接受长度决定，优化空间在"每步验证耗时"而非算法。
>
> **已完成**：按参考文章的分支配方（prefill CP8 + 分支内核）切换后，
> 128K 首字 11.47 s → **1.89 s（6.1×）**，5×300K 总耗时 196 s → **21.4 s（9.2×）**，
> 真实 agent 画像 30K 首字 2.09 s → **0.47 s（4.4×）**、解码 249 → **519 tok/s（2.1×）**。
> 详见 §7。

## 3. 测量方法

### 3.1 套件位置

| 文件 | 作用 |
|---|---|
| `bench/bench_suite.py` | 压测主程序 |
| `bench/bench_compare.py` | 两次运行逐场景对比 |
| `bench/merge_extra.py` | 补充场景并入结果集 |
| `bench/corpus/` | 固定代码语料（从 `/tmp` 归档，防丢失） |
| `bench/results/<tag>/` | `summary.json` / `summary.csv` / `raw.json` / `meta.json` |

### 3.2 可比性纪律（四条，不可破）

1. **salt 固定**：每条 prompt 首行注入 `## run=<salt> shard=<i>`，salt 只与"场景+轮次"有关、
   与运行标签无关 → 基线与优化后的 prompt **逐字节相同**，同时保证每次冷启动（实测
   `cached_tokens=0` 全场景成立）。
2. **输出长度固定**：`ignore_eos=true` + 固定 `max_tokens`，`temperature=0`，消除生成长度差异。
3. **并发请求各用不同语料文件**，请求之间不共享前缀。
4. **token 数一律取服务端 `usage` 回传值**，不信任客户端估算。

### 3.3 场景表

| ID | 场景 | 并发 | 输入 | 输出 | 轮数 |
|---|---|---|---|---|---|
| D1_1K | 单请求短上下文纯解码 | 1 | 1K | 256 | 3 |
| D1_30K | 单请求 30K 解码 | 1 | 30K | 256 | 3 |
| D1_128K | 单请求 128K 解码 | 1 | 128K | 128 | 2 |
| D1_300K | 单请求 300K 预填充与解码 | 1 | 300K | 128 | 2 |
| T8_1K | 8 并发吞吐 | 8 | 1K | 256 | 2 |
| T32_1K | 32 并发吞吐上限 | 32 | 1K | 192 | 1 |
| P_128K | 128K 冷预填充 | 1 | 128K | 32 | 2 |
| P_5x30K | 5 人同时开场 | 5 | 30K | 128 | 1 |
| P_5x300K | 5 人同时重上下文轮 | 5 | 300K | 128 | 1 |

### 3.4 指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| TTFT | 请求发出 → 首个非空 token（含 reasoning） | 受预填充与排队支配 |
| TPOT | (末 token 时刻 − 首 token 时刻) / (输出 token 数 − 1) | 受接受长度影响大 |
| **每步验证耗时** | `TPOT × 接受长度` | **剔除内容因素后的引擎真实解码开销**，单请求场景采集 |
| 解码 tok/s | `1 / TPOT` | = 接受长度 / 每步耗时 |
| 预填充 tok/s | `prompt_tokens / TTFT` | 并发时为单请求自身速率 |
| 输出吞吐 | 单轮输出 token 总量 / 单轮总耗时 | 并发场景的主指标 |
| 接受长度 | 服务端日志 `accept len` 采样（仅 rank0 行） | DSpark 投机解码效果 |

### 3.5 测量噪声（同配置连跑两轮，run1 vs run2）

| 指标 | 观测最大偏差 | 判定阈值（超出才算真变化） |
|---|---|---|
| TTFT p50（全场景） | 3.6% | **> 5%** |
| 预填充 tok/s | 3.7% | **> 5%** |
| 输出吞吐（T8/T32） | 5.1% | **> 8%** |
| 每步验证耗时（单请求） | 9.8% | **> 12%** |
| 解码 tok/s | 3.8%（接受长度相近时） | 见下 |
| 接受长度 | **最高 79%**（P_5x30K） | **不作判定依据** |

> **关键提醒**：接受长度是内容驱动的，且本部署的生成在多次运行间不完全可复现
> （8 卡 TP/EP 下 allreduce/GEMM 的非确定性会翻转近似同分 token，投机解码再放大差异）。
> 因此在"并发预填充挤压"场景（P_5x30K / P_5x300K）中，**TPOT 与解码 tok/s 的单轮偏差可达 ±40%，
> 不能作为优化是否成功的依据**；这些场景请看 TTFT、总耗时、吞吐。
> 解码类优化请用"每步验证耗时"判定。

## 5. 瓶颈分析（优化靶点）

### 5.1 靶点一：预填充吞吐随上下文长度下降，且与并发无关（最高优先级）

单请求预填充速率：

| 上下文 | 预填充 tok/s | 相对 30K |
|---|---|---|
| 30K | 13,731 | — |
| 128K | 10,810 | -21% |
| 300K | 7,646 | -44% |

并发验证（这是本次最重要的发现）：

| 场景 | 单请求速率 | 聚合速率 | 结论 |
|---|---|---|---|
| 单请求 30K | 13,731 | 13,731 | — |
| 5×30K 并发 | 2,812 | **14,060** | 与单请求持平 |
| 单请求 300K | 7,646 | 7,646 | — |
| 5×300K 并发 | 1,548 | **7,740** | 与单请求持平 |

**结论：引擎的预填充是"固定 token 速率"的资源池，5 个请求并发并不会让它变慢或变快，
只是把 150 万 token 串行排队。** 也就是说 P_5x300K 的 193s ≈ 1,496,145 / 7,740。
推论：
- 排队/调度层面的改动**不可能**降低重上下文场景的总耗时（前次 P1-1 shortest-prefill-first
  无效、P1-2 chunk 4096 负收益，与本结论一致）；
- 唯一有效方向是**提高 token 级预填充速率**（§6 的 C 组候选），或降低要预填充的 token 数
  （前缀缓存 / 上下文收敛）。

### 5.2 靶点二：队头阻塞（短请求被长预填充饿死）

1 条 128K 请求先发 0.5s，31 条 1K 请求随后同时到达：短请求 TTFT 全部落在 12.1~13.7s
（p50 13.15s），而长请求自身的 TTFT 为 12.65s —— 短请求几乎全部在长请求预填充结束之后
才开始，说明 chunked prefill 并未在长短请求间交错推进。

- 空载同请求 TTFT：0.187s
- 受压 TTFT p50：13.148s（**69×**）
- 当前 `schedule-policy=fcfs`，短请求 0.5s 后到达 → 天然排在长请求之后

这是交互体验上最容易被用户感知的问题，也是**唯一一个纯调度层面就能改善的靶点**。

### 5.3 靶点三：解码速度已由接受长度决定，引擎开销稳定

单请求"每步验证耗时"（= 引擎一次前向的验证成本）：

| 上下文 | 每步耗时 | 接受长度 | 解码 tok/s |
|---|---|---|---|
| 1K | 13.3 ms | 4.42 | 320 |
| 30K | 12.8 ms | 4.38 | 350 |
| 128K | 15.8 ms | 4.83 | 301 |
| 300K | 20.2 ms | 2.10 | 108 |

- 1K→30K 每步耗时几乎不变（注意力稀疏化生效），128K 起缓慢上升，300K 明显上升；
- 300K 的 108 tok/s 主要是**接受长度掉到 2.1** 造成的，不是每步变慢（20.2ms）；
- 因此解码侧有两个独立杠杆：**接受长度**（内容相关，难优化）与**每步耗时**（工程优化，本报告
  已给出基线 13.3ms @1K）。

### 5.4 靶点四：并发吞吐已饱和

| 并发 | 输出吞吐 | 每请求解码 | TTFT p50 | TPOT p50 |
|---|---|---|---|---|
| 1 | 260 tok/s | 320 | 0.187s | 3.1 ms |
| 8 | 875 tok/s | 192 | 0.788s | 5.2 ms |
| 32 | 1,254 tok/s | 78 | 2.329s | 12.8 ms |

8→32 并发：吞吐仅 +43%，TTFT 恶化 3.0 倍、TPOT 恶化 2.4 倍。
**`max-running-requests=32` 已越过吞吐拐点**，继续加并发只会牺牲延迟；
对交互式 CodingAgent 负载，8 并发是更好的工作点。

### 5.5 前缀缓存

30K 提示二次请求：TTFT 2.57s → 0.51s（-80%），命中 81.9% token。
缓存机制健康，运维纪律（固定系统提示词、不注入时间戳/随机 ID）仍是最大性价比手段。

### 5.6 显存余量（重要）

压测期间峰值 **71.7 GB/卡**（8 卡共 573 GB），单卡余量约 68 GB。
当前 B5 配方把 engram 大表（约 189 GB，按卡切分 23.6 GB/卡）放在**主机内存**换取显存。

原先考虑过把表回迁显存（A 配方，重预填充快 40%）。**参考文章的路子不同**：它同样把
engram 表放主机内存（`ENGRAM_HOST_TABLE=1`），但改成 `per_rank` 布局，并让**分片属主
直接写目标 rank 的对称内存**，把 CP 下的汇聚开销消掉（见 §6.1）。也就是说瓶颈不在
"表放哪"，而在"怎么访问"。因此本报告改为走文章这条路线，不再动 engram 位置。

单卡 68 GB 余量的价值转到别处：文章的 KV 容量实测 +31%（20.56M → 26.97M token），
余量可用于上调 `--max-total-tokens`，或抵消 CP 带来的额外激活显存。

## 6. 优化方案（对齐参考文章）

参考文章：**《DeepSeek-V4.1-Flash 的 SGLang H20 优化：长输入首字快 4–10 倍，开源可复现》**
（知乎 `p/2099263996943716515`，作者来自蚂蚁；代码 `github.com/antgroup/sglang`
分支 `dsv41-flash-h20`，head `6e6d5d9e13`，基线为社区 main `5884e4fe` @2026-10-27）。

### 6.1 文章做了什么

单机 8×H20-3e、`TP8 + prefill CP8 + DSpark` 下，文章分支 vs 社区 main：

| 指标 | 社区 main | 文章分支 | 倍数 |
|---|---|---|---|
| 冷 prefill TTFT，4K | 0.211 s | 0.092 s | 2.29× |
| 冷 prefill TTFT，64K | 2.966 s | 0.857 s | 3.46× |
| 冷 prefill TTFT，128K | 6.901 s | 1.724 s | 4.00× |
| 冷 prefill TTFT，256K | 17.681 s | 3.522 s | 5.02× |
| 冷 prefill TTFT，512K | 51.230 s | 7.476 s | 6.85× |
| 冷 prefill TTFT，1M | 163.386 s | 16.665 s | 9.80× |
| 解码吞吐，单会话 | 303 tok/s | 583 tok/s | 1.92× |
| 解码吞吐，32 并发 | 1,983 tok/s | 4,461 tok/s | 2.25× |
| 解码吞吐，64 并发 | 2,518 tok/s | 5,774 tok/s | 2.29× |
| KV 容量 | 20.56M token | 26.97M token | 1.31× |
| 冷启动到 READY | 1,850 s | 316 s | 5.9× |

三根支柱：

1. **prefill CP8**：把一条长请求的 token 按 interleave 摊到 8 张卡。关键是**通信不走 NCCL
   而走 NVLink 对称内存**——SWA KV 与压缩器汇聚在 q_b 之前由 copy engine 发出并与计算重叠；
   压缩器只投影本卡行再汇聚投影结果（尾部从"16384 行 GEMM + 全量汇聚"变成"2048 行 GEMM +
   输出汇聚"）；MoE 输入由 copy engine 直接拉取、按 rank 顺序 FP32 求和，省掉 all-reduce 与切片；
   engram 查表由**分片属主直接写目标 rank**。此外：稀疏 prefill 改回 `flash_mla_sparse_fwd`、
   晚层跳过（bounded replay，第 20 层之后只为最后窗口计算）、prefill CUDA graph 按精确行数
   懒捕获（消除每层约 4 ms 的 host 开销）。
2. **decode 去重复计算**：96 行起做 head↔row 交换（每卡只算 1/8 的行但用满 64 个头，
   64 并发下 FlashMLA 单次调用 257 μs → 47 μs）；64 行起加 TP-SP（每卡只留 1/8 残差流）；
   TP all-reduce 换 custom all-reduce v2（63 μs → 22 μs）；CUDA graph 按真实 batch 捕获；
   DSpark 的 verify argmax / draft 选词在词表分片上直接做。

### 7.2 关键发现

1. **预填充速率变成"与上下文长度无关"**：基线 30K→300K 从 13.7K 掉到 7.6K tok/s；

   而"速率随长度下降"这个缺陷基本消失。
2. **队头阻塞仍是结构性的，但代价小了 6 倍**：HOL 短请求 TTFT 13.148 → 2.103 s，

   要进一步改善只能靠准入/优先级调度，但 2 s 已落在可接受区间。
3. **bounded replay 让部分内容形态的接受长度下降**：D1_30K 的接受长度 4.38 → 2.39，

   §7.3 的消融证明：这个下降**不是** bounded replay 的系统性代价。
4. **可重复性很好**：两轮优化后测得的 TTFT 差异 ≤3%、吞吐 ≤5%、每步耗时 ≤1%。
5. 压测期间日志无 Traceback / CUDA error；功能校验（工具调用、思考模式、纯文本）全通过。

| T32 输出吞吐 | 1,254 tok/s | 2,544 | 3,261 | **3,253 tok/s** |
| 128K 预填充 | 10,810 tok/s | 27,004 | 65,650 | **66,911 tok/s** |
| 显存峰值 | 71.7 GB/卡 | 64.7 | 61.9 | **63.4 GB/卡** |

**一个必须知道的副作用**：冷启动的 5×300K 偶发 6 倍劣化（20.5 s → 124–133 s），
与图懒捕获无关，详见下一小节的定位记录。部署后建议先打一发 300K 级暖机请求；
压测时至少跑 3 轮取最小值。

**结论：单机上"识图 + CP8"已经同时拿到，不需要加机器，也不需要 EPD。**

#### 已知异常：5×300K 冷预填充偶发 6 倍劣化（2026-11-11 定位记录）

**结论先说**：冷启动的 5×300K 正常是 **20.5 s**；但约 **1/3 概率**会跑到 **124–133 s**（6 倍）。
劣化时 GPU 利用率 90%、功耗 415 W —— 是**在算**，不是等待。根因未定位。

**受控实验**（同一进程内，每轮都确认 `flush_cache` 返回 200、`cached_tokens=0`）

| 条件 | 结果 |
|---|---|
| 连续 8 轮冷跑同一批 5×296K | 第 1 轮 124.5 s，其余 **20.5–21.2 s** |
| 每轮前先发一个小请求预热 | 第 2 轮 132.8 s，其余 20.5 s |
| 错峰发送（50 / 300 ms） | 6 轮全部 20.5 s |
| 同 prompt 命中缓存（单发） | 0.7 s（冷 5.3 s 的 1/7.6） |
| 5 并发且全部命中缓存 | 3.2 s（GPU 利用率 0%） |

→ 与"是否空闲后第一发""是否错峰""是否命中缓存"都无关，是**随机**的。

**已排除的因素**

| 因素 | 证据 |
|---|---|
| 配置 | 两进程 `server_args` 逐项比对仅 `random_seed` 不同；其余 11 场景一致 |
| 前缀缓存 | 劣化轮 `cached_tokens` 全为 0；命中缓存反而 3.2 s |
| NUMA 绑核 | 补绑后仍复现，亲和性核对为 `0-119 / 120-239` |
| 磁盘 / 换页 | 逐轮采样 8 个 rank 的 `read_bytes` 与 `majflt`：**全为 0** |
| 请求抢占 | 无 retract/preempt 日志；慢轮总 `#new-token` 与快轮一致，无重复预填充 |
| 降频 / 他人负载 | SM 恒 1980 MHz；`nvidia-smi` 仅本部署 8 进程 |
| 到达时序 | 错峰 0/50/300 ms 无差异 |
| 图捕获 | `prefill graph stats`：`failed=0 low_memory=0`（整体重放占比约 9%） |

**当前应对**

1. 压测/评估这类场景**至少跑 3 轮取最小或中位数**，单轮不可信；
2. 生产上遇到重上下文并发明显变慢，**重试即可**（约 2/3 概率回到正常档）；
3. 日常 30K 级负载不受影响（`P_5x30K` 多轮稳定 2.2–2.3 s）。

**下一步**：`nsys` / `ncu` 可用（`/usr/local/cuda/bin/`）。需在 `nsys profile` 下重启服务、
连续压 8 轮以上抓到一次劣化轮，对比 kernel 时间，重点看 CP 的 all-gather /
head↔row a2a 是否走了非对称内存路径，以及 humming MoE 是否进入不同分支。

#### 后续：主机重启后劣化消失（2026-11-11 15:30 复测）

主机在 14:06 左右发生重启（`uptime` 归零、页缓存清空、GPU 无进程）。重启后按同一受控方法复测：

| 项目 | 结果 |
|---|---|
| 5×300K 冷跑，连续 8 轮 | **20.4 / 20.5 / 20.5 / 20.4 / 20.5 / 20.5 / 20.5 / 20.5 s**，劣化 **0 轮** |
| 每轮 `cached_tokens` | 全 0（确实冷跑） |
| 每轮磁盘读 / majflt | 全 0 |
| 全量 12 场景 | 与历史最好值一致（D1_128K 1.843 s、D1_300K 4.601 s、CHAT_30K 0.475 s） |
| 吞吐 | T8 1,943 tok/s（历史最好 1,958）、T32 3,319（历史 3,261）、CACHE 163.5（历史 162.8） |
| 启动 | 435 s（冷页缓存；热态约 315 s） |

**判读**：劣化**随主机重启消失**，且重启后 8/8 轮稳定 —— 说明它是**主机侧环境状态**导致的
（此前该机器已连续运行 8 天、期间经历十余次服务重启），不是部署配置或分支代码的问题。
具体是哪种主机状态（THP 退化、内存碎片、驱动/IB 状态等）未能定位，因为重启已把现场抹掉。

**因此当前口径**：

- 5×300K **正常值 20.5 s**，可作为基线；
- 历史上出现过的 124–133 s 属于**环境异常态**，不是本配置的固有性能；
- 若再次出现，优先怀疑主机状态，处理方式是重启主机或至少重启服务后复测；
- 压测纪律仍建议保留：≥3 轮取最小值，单轮不可信。

**在定位前，5×300K 按 20–135 s 区间看待，不作稳定基线**（其余 11 场景不受影响）。

cd bench

**判定纪律**（`bench_compare.py` 已内置这些阈值，输出里直接标 `✅ 改善 / ❌ 劣化 / ≈ 噪声内`）：

4. P_5x30K / P_5x300K / HOL 的 TPOT 与解码 tok/s 只输出参考值、不给判定（噪声过大）；
5. 任何改动都不得让其他场景劣化超过上述阈值，否则视为负优化。

## 9. 附件与已知限制

**原始数据**：未随仓库发布（体积与脱敏原因），可用 `bench_suite.py` 在当前机器重跑复现
（`summary.json` 机器可读、`summary.csv` 表格、`raw.json` 逐请求、`meta.json` 配置快照）。

**已知限制**：
1. 接受长度采样依赖服务日志（`logs/server-latest.log` 的 `Decode batch` 行），
   并发场景下只能取窗口均值，无法归属到单个请求；
2. 生成结果在多次运行间不能逐 token 复现（§3.5），这是部署本身的特性，不是测量缺陷；
3. GPU 时钟模式未采集（`nvidia-smi` 观察 1980 MHz，未做锁定），
   若后续出现整体性偏移，应先排查时钟与同卡租户；
4. D1_300K 由补充运行并入（`merge_extra.py`），与主表其余场景非同一次进程内采集，
   但 TTFT 与预填充速率两轮偏差仅 0.1%，可放心引用。
