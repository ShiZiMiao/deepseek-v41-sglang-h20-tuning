# DeepSeek-V4.1-Flash-1017 真实场景性能验证报告

> 日期：2026-11-03　服务：配置 A 生产态（DSpark=ON，TP8/EP8，KV 池 3M）
> 负载形态：OpenCode 式日常开发——代码仓库语料（精确 token、真实代码 token 分布）、
> 3 个 tools 定义（read_file/write_file/run_command）、`reasoning_effort: "low"`、

> 场景口径修正：**首轮上下文 ≤30K**（用户确认），500K/300K 为会话累积后的

## 1. 场景与结果总表

解码速度 = 1/TPOT（单请求流式出 token 速率）。TTFT 为首 token（含 reasoning）。

| 场景 | 上下文 | 并发 | TTFT (s) | TPOT (ms) | **解码 tok/s** | 总时长 | accept |
|---|---|---|---|---|---|---|---|
| **S0 单人·首轮** | 30K 冷 | 1 | **2.11** | 3.2 | **313** | 3.4s | 4.02 |
| **S0M5 多人·5 人同时开场** | 30K×5 冷 | 5 | 0.67 / 2.84 / 4.99 / 7.16 / 8.23 | 5.1~57.6 | **17~196**（中位 81） | 9.1~13.9s | 4.01 |
| **S1b 单人·续轮**（同前缀命中缓存） | 500K 热 | 1 | **0.85** | 4.9 | **204** | 3.2s | 3.36 |
| **S1a 单人·重上下文轮** | 500K 冷 | 1 | 85.7 | 7.0 | **143** | 92.9s | 3.35 |
| **S2 多人·3 人重轮** | 300K×3 冷 | 3 | 38.5 / 76.2 / 112.7 | 9~81 | **12~111**（中位 22） | ~122s | 3.85 |
| **S3c 多人·5 人重轮** | 300K×5 冷 | 5 | 38.8 / 76.5 / 113.7 / 151.4 / 188.0 | 11.2~362 | **2.8~89**（中位 12） | ~191-198s | 4.02 |

## 2. 解码速度专项（tok/s）

| 维度 | 解码 tok/s | 说明 |
|---|---|---|
| 单人稳态（30K 上下文） | **313** | 首轮即达交互流畅 |
| 单人稳态（500K 上下文） | **143~204** | 上下文越大每步注意力成本越高；续轮（热）204 |
| 5 人并发开场（30K） | 17~196（中位 81） | 轻度挤占，打字体验仍流畅 |
| 3 人并发重轮（300K 冷） | 12~111（中位 22） | 他人预填充窗口内被挤占 |
| 5 人并发重轮（300K 冷） | 2.8~89（中位 12） | 最坏 2.8（恰逢 4 条 300K 同时预填充） |

规律：解码速度主要受 **上下文长度** 与 **并发预填充挤占** 两个因素影响；
DSpark 投机解码在真实代码负载 accept 3.35~4.02（理想文本 5.999）。

## 3. 结论

1. **单人使用：优秀，无需调整。** 真实画像（首轮 30K）首 token 2.1s、解码 313 tok/s、
   3.4s 完成一轮（含工具调用）；会话中后段命中前缀缓存的续轮 TTFT 0.85s。
   仅在"整轮替换 500K 全新上下文"这种极端冷轮才出现 85.7s 预填充。
2. **3~5 人使用：开场体验好，重上下文轮建议错峰。** 5 人同时开场（30K×5）全部
   14 秒内完成、TTFT ≤8.2s；而 5 人**同时提交各自 300K 冷上下文**时 TTFT 排队至
   188s、解码最低 2.8 tok/s。现实中团队共享同一仓库前缀时会大幅缓解
   （实测命中缓存的请求 TTFT 仅 3~3.5s）。
3. **上下文增长是自然缓坡而非悬崖**：agent 会话逐轮增长（首轮 ≤30K → 中后段数百 K），
   大预填充成本被分摊到各轮，且同前缀续轮免费。
4. **保持稳定前缀**是关键运维纪律：系统提示词勿注入时间戳/随机 ID，否则缓存失效、
   每轮都付全量预填充。
5. 资源余量：1.5M token 并发预填充 198s 内完成，未触及 32 并发上限。

## 4. 建议

| 项 | 建议 |
|---|---|
| 单人 500K 峰值 | 直接支持，无需收敛 context-length |
| 团队使用 | 开场随意；多人同时"全量刷新大上下文"时错峰或共享仓库前缀 |
| 客户端配置 | 保持每轮前缀稳定；`reasoning_effort: "low"` 为日常推荐档 |
| 监控关注 | 解码 tok/s 与 accept（真实值 3.3~4.0），低于 2.0 或 accept <2 需排查 |

## 5. 性能优化逐变量验证（2026-11-04 补充）

同输入、唯一前缀全冷、逐变量独立重启（R0b 基线 vs 变体）：

| 项 | 判定 | 关键证据 |
|---|---|---|
| P1-1 调度策略 shortest-prefill-first | ❌ 无效 | 同尺寸场景差异<2%；**MIX 混合长度场景**（30K~500K 五档同发）差异<1%，短上下文 TTFT 本就不被阻塞（30K 仅 3.05s） |
| P1-2 chunked-prefill 4096 | ❌ 负收益 | 5×300K 总耗时 +6%（213.7 vs 201.3s），解码挤压无改善 |
| P2-1 NUMA 绑核 | ✅ 已生产化 | 5×30K 并发 TPOT p95 30.4→12.5ms、解码最低 33→80 tok/s；start.sh `NUMA_BIND=1` 默认开启 |
| P2-2 DeepGEMM 预编译 | ✅ 已固化 | 预编译 935s 完成；热机启动 647→595s（约 8%）；冷机/缓存失效场景价值大 |

**MIX 混合长度场景**（5 人处于会话不同深度同时发轮，最贴近实际开发）：

| 会话深度 | TTFT | 解码 tok/s | 全员完成 |
|---|---|---|---|
| 30K / 80K / 180K / 320K / 500K | 3.05 / 9.34 / 27.15 / 68.51 / 152.12s | 6.2~65.4 | ~167s |

结论：各档 TTFT 正比自身上下文（chunked prefill 交错推进，短请求无队头阻塞）；
并发预填充窗口内解码被 GPU 算力争抢压至 6~10 tok/s——此为物理瓶颈，配置旋钮无解，
缓解靠使用侧（错峰大轮次/稳定前缀）。
